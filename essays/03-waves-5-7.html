Seen to Fail

What three waves built for prediction and for the synthetic copy, why its rules arrived with tests that had failed without them, and what that costs.

The second essay left v3 able to count, in queries that cannot quote a row, how many of an environment's rows break each of six kinds of rule, and to name a change's operation provisionally. The 50 commits from 77544d6 to 28d6bd7, on 20 and 21 October, hold waves 5, 6 and 7 of the build. They make every part of a prediction but the verb that runs it: io reads DacFx's script statement by statement, the BlockOnPossibleDataLoss checks among them; a vocabulary of 72 rows says what each statement asks of the rows; and every sample change of the corpus is predicted on an empty, a populated and a violating copy. They also build the copy a proof will run on: a plan of rows that reads no row, a local server whose copies are swept, cached and dropped one session at a time, and synthetic-copy up, which plants an environment's answers into a copy of the repository's schema and counts the copy again to see that it gives them back.

One habit holds across the three waves: a rule is trusted once a test has failed without it. A fix arrives with the test that fails on the code before it, and the commit says which. A review's finding is pinned by the mutation that restores the defect, and a table of rows by removing each row in turn. A race that 3,200 concurrent calls did not reproduce is pinned by a directory planted where DacFx writes its script. Where a test was not seen to fail, the commit says that too.

io · kernel · tests

The check, matched on the parse

Essay two quoted the sentence DacFx writes for BlockOnPossibleDataLoss, byte for byte the same in 162.5.57 and 170.5.96, and three lookalikes a text match would take: a table rebuild's copy step under the same IF EXISTS, the RAISERROR at state 127 that verifies a constraint added WITH NOCHECK, and the check quoted in the golden pre-deploy script's comment. WP 2.2's reader, io/BlockOnPossibleDataLoss, decides by the parse. It turns the plan's script to LF, empties each SQLCMD command line so that a line of the parse is a line of the script, substitutes each $(var) in memory, parses the rest with TSql160Parser, and keeps an IF of one shape alone:

if (node is { Predicate: ExistsPredicate exists, ElseStatement: null }
    && node.ThenStatement is RaiseErrorStatement { ThirdParameter: IntegerLiteral { Value: State } })

The copy step's IF holds a BEGIN … END, the verification's IF tests @@ROWCOUNT, and a comment is no statement, so none of the three matches. A check's sites, the statements it protects, are the paragraphs of the block comment DacFx writes just before it, since the script names those statements nowhere else (DECISIONS.md:163).

The predicate runs as SELECT CASE WHEN EXISTS (…) THEN 1 ELSE 0 END through SqlServer.Measure, written back by io's Sql160ScriptGenerator and admitted again by the allowlist, so the text that reaches queries.log is one the allowlist parsed. ScriptDom 180.102.0 writes a subquery's QuerySpecification on its own without its WHERE clause, so the query is written from the whole ExistsPredicate, and the comment above that line names the release. None of the checks in the twelve committed files of DacFx's checks has a WHERE clause, so the fixture test writes one: its check's WHERE converts a planted value and fails with Msg 245 against an environment classified real. Without the WHERE the query would answer 1 and raise nothing. With it, the failure reports Msg 245 and the check's site, and the planted value appears in neither the error nor queries.log.

A SQLCMD value that a reference resolved is marked sensitive. SqlCmdVariable.Substituted records where it placed each value, so the reader knows where a secret sits without searching the text for it. A check whose span holds one, from the first character of the comment before it to the end of the IF, is refused as sqlcmd.sensitive, naming $(ServiceToken) and never its value. The span starts at the comment because the comment's paragraphs become sites, and sites reach the prediction's output.

One fix landed before the reader, in 1f2a47e. On the windows-latest LocalDB job, run 39372494078, DacFx 170.5.96 returned a null script for one plan of S2's fixture. Given no path, DacFx writes <temp>/<database>_Update<n>.publish.sql, choosing n by File.Exists and then File.Create, and deletes the file once read; the fixture planned three times at once under one database name. io/DacFx.Scripted gives each call a folder of its own. 3,200 concurrent calls on Linux reproduced nothing, so the fast test plants a directory at <temp>/<database>_Update1.publish.sql, which DacFx cannot open as a file; before the change every plan failed there with Access to the path … is denied.

A count, a person, or neither

The seven kinds differ in who can answer them, and kernel/Preconditions.Kinds.cs gives each kind two facts. Declared is true for Computed and Authored, whose state a person declares and no count gives. Breakable is false for Scan and Rebuild, which read every row and fail on none. Outcome.Predict blocks only on a breakable kind that is violating, and refuses a declared kind with no state as plan.undeclared, whose remedy is Look at the rows the statement reads in the environment, and declare a witness row for each shape it meets, or that it meets none. Every Match over the kinds now takes thirteen cases.

KeyLength is the one new kind whose violations io counts: the rows whose key passes 900 bytes under a clustered index or 1,700 under another, on which CREATE INDEX fails with Msg 1946. io/AggregateQueries.Length.cs counts the DATALENGTH of the key's one column of varying width against what its fixed columns leave of the limit, converted by TRY_CONVERT first where the change retypes it. The fixture test holds that count to SQL Server's own. On an nvarchar(1000) column it plants rows of 850 characters (1,700 bytes) and 851, a NULL and an empty string; the count reads one violating row of four, CREATE NONCLUSTERED INDEX fails with Msg 1946, and once the row of 851 is deleted the index builds over the rest. A key of two varying columns, whose rows pass the limit by two values together, and a key whose fixed columns alone pass it, which SQL Server refuses even on an empty table (Msg 1944), read not predictable read-only; so do Temporal, whose count compares two columns of one row, the period's start and end, and SeedDrift, whose count would send the seed's own values; no form of the allowlist holds either.

Four wrong answers

Four wrong answers were found in WP 2.1's second slice, WP 2.1b, after its first commit. One, fixed in 30a1d03, depended on the order of a key's columns. The other three were among the six defects the slice's verification found, which b04a203 fixes; its message lists the tests, under the line Each fails with the old rule restored.

SortedArray orders a key's columns by name, so in CREATE INDEX [IX_N_Big_Id] the nvarchar(max) column [Big] came before the int [Id]. KeyBytes stood for the max column with long.MaxValue and then added the int's 4 bytes. C#'s + is unchecked unless a project sets CheckForOverflowUnderflow, which none of v3's does, so the total wrapped negative, no KeyLength was raised, and the index read as a Scan. The planter summed the same sizes with Enumerable.Sum, which is checked, and threw OverflowException. The one overflow was silent in one place and an exception in the other. KeyBytes now stays at long.MaxValue once a max column is counted, in either order of the columns:

total = bytes == long.MaxValue || total == long.MaxValue ? long.MaxValue : total + bytes;

A Computed or an Authored on a table the change creates was answered by Coordinates.Of as a count of no rows, which ExistingData.Of rejects with an ArgumentException: the chain WP 2.5 assembles ended in an exception where an error with a remedy belongs. What an extract keeps

A copy can stand in for an environment only where DacFx treats the two alike, and the Facsimile left three questions about that open, its §11 questions 1, 9 and 10. Spikes S9 to S11 answer them in Io.Tests: SpikeReceiptTests, on 170.5.96 in process and on 162.5.57 through tests/DacFx162/, which gained the verbs extract and constraints.

S9 asks whether an extract keeps a constraint's trust. A helper folds the catalog's two bits into one number, is_disabled × 2 + is_not_trusted, and −1 for a constraint the database lacks; a disabled constraint is untrusted too, so it reads 3. LoadFromDatabase and Extract keep Disabled as a public property. Untrusted survives only as model.xml's IsNotTrustedPropertyAnnotation, which no public property exposes, and io's own element reader reads the untrusted key exactly as the trusted key add-a-foreign-key builds. No plan of the repository touches the untrusted key, and no publish trusts it again. A project cannot declare a key untrusted either: its build warns SQL70588 at OrderStatusText.sql(30,1), WITH CHECK | NOCHECK option for existing data check enforcement is ignored, and its package holds the key trusted. So trust has to come from the environment's catalog (DECISIONS.md:175). The test names its own weak point: it asserts on the internal annotation's name, so a DacFx release that renames it fails the test, which runs again on every bump of the pin.

S10 asks when validation runs. The plan of add-a-foreign-key-whose-parent-the-seed-adds must hold, in this order, the key added WITH NOCHECK, COMMIT TRANSACTION, the post-deploy script's header, the seed's row for Customer 999, the post-deploy script's last line, DacFx's Checking existing data against newly created constraints, and WITH CHECK CHECK CONSTRAINT [FK_Order_Customer_CustomerId]. A lookup row the post-deploy script seeds therefore satisfies a new key. With a second orphan that no seed fixes, the publish fails with Msg 547 and leaves Customer 999 seeded and the key added and untrusted: a block at validation is not atomic, and a proof reads the state after it.

S11 asks whether system names survive. SQL Server names an unnamed default after its object id, and two fresh databases allocate the same ids, so the test gives the environment a history of two tables created and dropped. SQL Server Express and LocalDB create a database with AUTO_CLOSE ON, and the publish that sets it OFF restarts the database, after which it allocates object ids as if the dropped tables had never existed; the helper sets AUTO_CLOSE OFF first, as an environment's is. With history the DF__Note__Body__ names differ, the plans' operations are equal, and the scripts are equal once each system name's hex suffix is replaced by a placeholder. Spike S11 also found that every plan drops and re-creates a check written with IN, which SQL Server stores as a chain of ORs and DacFx compares as text. Check drift stays strict at exit 5 and now names the cause, with the OR form as its remedy (drift.check-written-with-in).

io · ci

A copy's lifetime

A synthetic copy needs a local server that makes, caches and drops databases without leaving them behind and without two runs meeting. WP 3.4 completes io/LocalServer.

The sweep runs before each copy is made. It picks the rows of .dbchange/copies.json that name a copy of this machine, on the local server as this machine names it now, made more than a day before a clock its caller passes; a row with no readable time counts as old, and nothing the registry does not hold is chosen. The day stands in for a liveness check across processes: a copy younger than a day may still be held. The test kills a child process holding its copy, plants three rows beside it, another machine's, another server's and one made a day later, and makes the next copy by a clock set a day and a minute past the killed one. The killed copy goes; the three planted rows and the new copy remain.

Two drops of one copy at once, by two sweeps or by a sweep and a Drop, failed in 1 to 10 of 20 rounds through sqlcmd on SQL Server 2022 Express: one session's SET SINGLE_USER WITH ROLLBACK IMMEDIATE killed the other's at severity 21 (Msg 596), which closes the connection before a CATCH runs. A kill at severity 21 cannot be caught, so the drops are kept apart. One batch, sent to master on an unpooled connection, takes a lock its session owns and drops under it:

EXEC @held = sp_getapplock @Resource = @lock, @LockMode = N'Exclusive', @LockOwner = N'Session', @LockTimeout = -1;

The session owns the lock because DROP DATABASE cannot run inside a user transaction, and the second drop then finds DB_ID null. A database a failed or killed RESTORE left RESTORING takes DROP DATABASE alone, since SQL Server refuses ALTER DATABASE on it (Msg 5052). The test runs two Drops and two sweeps on one Barrier in each of 12 rounds; it was red against the earlier DROP. A statement to a copy is sent once more after two seconds only when its connection never opened, and only while the server has not yet answered this process once, since a failure after the connection opened may have run a CREATE or a DROP. Against a TCP listener that accepts each connection and closes it, the build test counts two connections and a run that fails as server.unreachable, with no row left in the registry.

A fresh copy of a base is restored from a backup or published from scratch. The plan put the backup in .dbchange/cache/, which SQL Server 2022 Express, running as the mssql user, cannot write; only LocalDB runs as the caller. So LocalDB writes there; a SQL Server on this machine writes into SERVERPROPERTY('InstanceDefaultBackupPath'), under a name carrying 8 hex digits of the checkout's path, so two checkouts at one base never share a file; and a server on another machine has no cache and publishes its base each time, with the note cache.unavailable (DECISIONS.md:180). Spike S4 timed the choice in CI on 300 generated tables, OSUSR_S4_T001 to OSUSR_S4_T300, each with an IDENTITY key, two defaults and a reference to the table before it, and a CHECK on every tenth.
