Measured Beside

What two days of work built for prediction, why each part stands next to the thing it claims about, and what that costs.

The first essay left v3 able to read an environment and say nothing it should not. In the 63 commits from c1ce443 to 77544d6, on 19 and 20 October, it began to predict. The kernel learned what a change asks of the rows an environment already holds, where those rows are, and whether the change blocks. io learned to count the rows that would break each rule, in queries that cannot quote one. A classifier names the operation from patterns kept as data. The code took a shape a reader can hold, the local server left Docker, and M2 started on the operator's go.

One habit runs through all of it: each claim is made beside the thing it is about. The Fits count runs beside the ALTER COLUMN it predicts. DacFx 170.5.96 plans beside 162.5.57. v3's schema is read beside v2's own read side. And the read-only trace now watches dbchange run as its own process, which found a promise the tests had kept by accident.

ci · tests · io

A file one reading holds

On 19 October the operator ruled that a package's ceiling may rise and a file's may not. A C# file of kernel/, io/ or cli/ holds 500 lines and 140 characters a line; a test file holds 800 lines. Budgets names each file and line over, and pins how it counts: a tab is one character, a surrogate pair two, a trailing carriage return none.

The reflow turned width into height. io grew from 5,203 to 6,221 lines with no change of meaning, and io/SqlServer.cs reached 1,196. It became a partial class whose members moved whole into files named for their concepts: SqlServer.Measure, .Query, .Reference, .Allowlist. One move was declined. C# orders static initializers within a file and promises nothing across the files of a partial class, and one timeout reads the other:

internal static readonly TimeSpan CommandTimeout = TimeSpan.FromSeconds(30);
internal static readonly TimeSpan AggregateQueryTimeout = CommandTimeout;

So both stay in SqlServer.Query.cs, and the split's review compared io's IL before and after to show that every static constructor kept its assignments. A package budget alone says how much code there is, and nothing about whether one file can be read at a sitting.

ci · io

A server nobody starts for you

The team's laptops run LocalDB 16.x and the environments' network has no Docker (DECISIONS.md:103), and a copy proven in a container proves something about a machine nobody on the team has. On Linux, ci/sql.sh up now installs SQL Server 2022 Express from packages.microsoft.com and runs sqlservr as the mssql user on 127.0.0.1; on Windows, ci/sql.ps1 up starts LocalDB.

Each edge takes a line or two. Microsoft packages SQL Server 2022 for Ubuntu 22.04 alone, so on 24.04 the missing libldap-2.5 comes from Launchpad's librarian, pinned by SHA-256. Microsoft's key is trusted only under its release-signing fingerprint. sqlservr starts with the caller's environment emptied but for its own settings, PATH and HOME, so a daemon that outlives the session holds none of its tokens. ci/sql.sh conn prints a command that reads the password when evaluated, so no captured output holds it.

Its one failure was silent. On a runner that had never seen mssql-server, dpkg-query exited 1, pipefail carried the status into an assignment, and errexit ended the script before the install began: both Ubuntu SQL jobs of f66521f died in 40 ms. The cloud session never met it, because mssql-server was installed there before the function existed. The fix keeps its reason on the line above:

# dpkg-query exits 1 for a package it does not know, which pipefail would carry into `had="$(installed)"` and errexit end silently.
installed() { { dpkg-query -W -f '${Status} ${Version}' mssql-server 2>/dev/null || true; } | sed -n 's/^install ok installed //p'; }

io starts nothing. LocalServer.Choice takes DBCHANGE_SQL, then the server sql.env names, then LocalDB; a missing one is exit 4 whose remedy names the script. The choice is a closed record whose ToString prints its kind and never its connection, and the doctor asks the same function the copies do.

kernel

Data-blind, as a property

v2's central finding is a sentence about DacFx: the BlockOnPossibleDataLoss check fires on "the table merely having a row" and "never inspects the column at all". v3 states it as a property. A Precondition names a table, the columns a rule reads and one of six closed kinds: TableEmpty, NotNull, Fits, ForeignKey, Unique, Check. ExistingData holds two booleans for each, derived from counts, so no row's value reaches the kernel. Outcome.Predict reads TableEmpty by presence alone:

var because = SortedArray.Of(states.Where(s => s.Precondition.Kind is PreconditionKind.TableEmpty ? s.Populated : s.Violating));

Law 9's test samples sites, preconditions and states, then hands Predict existing data no count could produce, a populated table recorded clean, and asserts that the change blocks all the same. The property is tested against the input most likely to fool it. A change stopped where that check meets a NotNull or Fits on a populated table ships in two releases, v2's finding F4.

Two rules beneath carry measured facts. Coordinates answers a table the change creates with no rows, counts a renamed object under the name the environment holds, and refuses an object the environment lacks, which is "never counted as empty". A column the change adds holds NULL in every existing row when it allows NULL, whatever its default, because DacFx 170.5.96 adds it with no WITH VALUES. And ColumnType holds a type with its five facets and no ordering between types. The kernel never calls a retype a widening; it hands both types to io, which asks the server.

io

Asking in a form that cannot answer with a value

WP 2.3 turns a table's preconditions into the items of one SELECT, built as a ScriptDom tree and checked by the allowlist the first essay admired. Its summary states the rule: ask SQL Server how many rows break the rule "rather than re-deriving SQL Server's answer". For Fits, a row violates when its value is not null and its TRY_CONVERT to the new type is:

All([Is(Value(), isNull: false), Is(new TryConvertCall { DataType = target, Parameter = Value() }, isNull: true)]);

No builder writes CONVERT, CAST or PARSE, so no failed conversion can write a row's value into an error, and a check's implicit conversion is written in the TRY_ form SQL Server would plan.

The care is in the measuring. One fixture test plants, in each of eighteen columns, a value too long and one that fits or a NULL, counts them, then runs each ALTER COLUMN beside the count. int into nvarchar(2) fails with Msg 8115; int into varchar(2) succeeds and writes '*'. A table of type widths would get one of the two wrong. varbinary into a shorter type drops trailing 0x00 bytes and refuses any others, which no admitted query can tell apart, so that retype reads not predictable read-only, with its reason. The code says when it cannot count.

Unique groups duplicates in three steps, by the bytes, by a binary collation, then by the index's own, because SQL Server refuses an aggregate over an aggregate (Msg 130); the steps sort duplicates into exact, trailing space, case and accent. The plan had said each table is scanned once, and a decision line corrected the plan to the code: one statement per table, in which each key's grouping reads the table again. The text ScriptDom writes back is checked a second time, because the generator writes a COLLATE name unquoted. Every count carries session.unverified until spike S7 reports the Octopus login's language and date order.

kernel · tests

Names, held provisionally

v3 keeps its naming rules as data: 21 operation files under tests/Golden/patterns/, each with a block a person can read.

recognize:
  match: altered Column Nullable:true→false
  ships: two releases on a populated table; one release, in place, on an empty one

Classify.Of groups a change into entries, a column in its table's, a created history table in the entry of the table it versions, and asks every block of every entry. One rule keeps the matcher honest: a clause recognizes an alteration only when its conditions account for every property the alteration changes. A column taken from nvarchar(40) NULL to nvarchar(80) NOT NULL is no widen and no make-mandatory; it is "unclassified change: prove it". A matcher that checked only a clause's own conditions would name it both, with two shipping shapes that contradict each other: in place, and two releases.

Every summary begins with provisional, which only a proof may drop; v2 wrote that rule as advice to an agent, and here a test reads it. The refusals are where Classify earns its place. A rename made by typing, with no refactorlog entry, publishes clean: v2's tests watched a renamed table come up empty beside the old one, still full, and a proof would report applies. So Classify reads the shape, a dropped and a created column of one type at one ordinal, a table dropped and created with the same columns, a name moved between schemas, and refuses each with the remedy that writes the entry.

tests · DacFx

One sentence on two releases

Spike S2 asked whether DacFx 162.5.57, the pipeline's presumed release, writes the BlockOnPossibleDataLoss check as the committed 170.5.96 does. tests/DacFx162/ answers from inside the build: the one project that overrides a central package version, referenced by none, a console the fixture tests start as a child process with its connection string in an environment variable, never an argument. The answer is one sentence, byte for byte in both releases:

IF EXISTS (select top 1 1 from [dbo].[Customer])
    RAISERROR (N'Rows were detected. The schema update is terminating because data loss might occur.', 16, 127) WITH NOWAIT

tests/Golden/data-loss-checks/ holds the extracted checks for 11 of the 40 sample changes, never a whole script, and a change with no file is the claim that its plan writes none. Finding the sentence takes a parse. A table rebuild's copy step opens with the same IF EXISTS; a constraint added WITH NOCHECK is verified by a RAISERROR at state 127 with another message; and the golden pre-deploy script quotes the check in its account of v2's disproven backfill, so v2's finding rides into every plan as a comment. The test reads none of the three as a check. The releases differ in one block, Query Store's: unset, it is OFF to 162.5.57 and READ_WRITE to 170.5.96. The test pins that block and compares the rest.

kernel · ci

v2 as the oracle

WP 3.1 gives the planter its typed Schema and Order, the order it inserts in, and proves them by the strongest kind of proof the parity ledger knows: a differential against an independent oracle, here v2. v2's CLI writes no read-side catalog, so ci/readside.sh writes a short F# program that calls ReadSide.readSchema and CatalogCodec.serialize, and builds it from the archive with v2's pinned .NET 9.0.314 SDK, outside the repository, every bin/ and obj/ under .dbchange/readside/. The Ubuntu lane runs it on every push and holds the committed facts equal to v2's; the other lanes compare v3 with those facts, which cannot go stale while that lane is green. The facts file opens with what it leaves out and why, from foreign-key names, which v2 makes up, to trust, which DacFx's model does not hold.

Order runs Tarjan's components over every reference, defers each optional reference inside a cycle, finds the mandatory cycles and places the rest by Kahn's algorithm, smallest name first. The golden copy's one mandatory cycle is Egg and Hen. The doc comment names the price of the simple rule: it can defer a reference the planter did not need deferred, "and changing that changes WP 3.8's planted rows". A minimal set would need a feedback-set solver. This one a reader can check by hand.

io · tests

A promise kept by refusal

M1 closed on a promise and a test that watched it: the read-only principal sends no DML, no DDL and no EXEC (R14), and an Extended Events session on its login records what it sends. On 19 October a reviewer of WP 2.4 saw the fixture lane go 54 of 55, that test failing on exec xp_msver @optname=N'Platform'. It passed alone and on a rerun, and the note called it intermittent.

The next wave measured it. DacFx 170.5.96 asks xp_msver for the host's platform, processors and memory on any connection whose data source and database its per-process cache does not hold, for telemetry dbchange turns off; the login is not in the key. The test ran dbchange inside the test process, where the admin's publish had already filled the entry, and whether the call appeared depended on what the process had touched before. The published dbchange starts cold and sends it twice for every read and every check drift. The test had kept the promise by accident.

The operator kept the promise as written (DECISIONS.md:143). io/ServerProbe watches SqlClient's WriteCommandBefore event and throws for exactly a call of xp_msver, as a stored procedure or a one-statement batch, reading no parameter and logging nothing. DacFx catches it and goes on without the figures; a release that stopped catching it would fail the read as dacfx.failed. Only cli's Main installs it, since only in dbchange's own process is every connection dbchange's, and the trace now runs the published dbchange as its own process. Against an observer that refuses nothing, it failed with six xp_msver calls.

Twice in two days a warm machine hid a failure: a session with mssql-server already installed, a process with DacFx's cache already full. A cold path found each.
